Site Optimization Review

还能优化什么

前几轮把技术层基本做完了：sitemap 与 noindex 零冲突、canonical 全自指、 每页恰好一个 h1、图片管线带 srcset、分类页放行、JSON-LD 逐篇取图。 这次实测下来，剩下的问题几乎全在内容侧——模板不用再动，动的是文章和 front matter。

02P1 · 正文内链：90% 的文章一条都没有

P1 文章之间是「并列」的，不是「网状」的

实测 133 篇文章的正文（<content> 内部）指向其他文章的链接：

指标值
正文内链为 0 的文章120 / 133（90%）
有内链的文章13 篇，最多的一篇 11 条
全站正文内链总数34 条

注意这不是「孤儿页」问题。每篇文章的入链中位数是 13 次，全部来自 /posts/、/archive/、首页和相关文章块——Google 爬得到，两天内就能收录。 缺的是语义关联：

  1. 权重无法按主题聚拢。列表页给的链接是「按时间排的」，没有主题信号； 一篇文章提到「降噪耳机」，另一篇讲「通勤装备」，两者之间没有链接，Google 就不知道它们相关。
  2. 相关文章块是模板算的，不是作者指的。它按共享标签打分（阈值 20）， 标签本身有 74% 只用过一次，所以推荐质量受限于标签质量——这跟第 03 节是同一个根因。
  3. 读者的阅读路径断了。读完一篇想顺着看下去，只能回列表页重新挑。

为什么不能「批量补」

一次性给 120 篇各塞 3 条链接，会造出大量「见《xxx》」式的空洞锚文本， 既不像人写的，也容易被判为链接农场。这件事只能顺着写作节奏做：

可执行的做法（按性价比排）
  1. 新文章发布时补两条：写完先别发，从旧文里挑 2 篇真正相关的， 在正文里自然引用一次（锚文本用那句话本身的词，不要写「点击这里」）。一次两分钟，一年下来就是 260 条。
  2. 老文章「回链」：新文提到旧文时，顺手去旧文里补一句「后来在《新文》里又聊过」。 单向链变双向链，是内链里最值钱的一种。
  3. 每季度挑 20 篇补一轮：优先补「入链最少」的那批—— 当前最低的 6 篇是 good-news-and-good-feelings、partner、 talk-about-topics、personal-profile、 music-sharing、trip（各 7–8 条，全部来自列表页）。

如果愿意，我可以写一个 scripts/suggest-links.py：输入一篇文章， 按「共享标签数 + 分类相同 + 时间接近」排出 5 篇最该链的旧文，写新文时跑一下就有候选。 它只读 front matter，不改任何文件。

P1 标签在当「关键词」用，而不是当「主题」用

标签页现在是 noindex（这个判断是对的：157 个标签页各自只有 1 篇文章， 和文章本身几乎同构，放行只会给 Search Console 添一堆「已抓取 - 尚未编入索引」）。 但标签还有第二个用途——它是相关文章打分的唯一输入。 74% 的标签只出现一次，等于大部分标签对推荐毫无贡献。

建议：157 个单次标签里有 10 组明显的同义簇

这些标签是同一个话题的不同说法，归并后话题密度立刻上来：

这 10 组覆盖约 95 个单次标签。归并后总量大致是 10（新簇）+ 24（2 次）+ 12（3 次）+ 19（≥4 次）≈ 65， 正好落在「标签有意义」的区间。单篇 2–4 个标签的写作习惯不用改。

⚠️ 两个技术前提
  1. 改的是文章 front matter 的 tags 数组，不是建新文件。 旧的 /tags/<词>/ 页会随之消失（它们本来就 noindex，SEO 无损）， 但会留下 157 个 404 —— 要顺手在 static/_redirects 里加 301 到新簇。
  2. 不要一次改完。先挑 2–3 组（比如「数码设备」「饮食减脂」）试一遍， 看相关文章块的推荐质量有没有变化，再决定要不要继续。

04P2 · 分享卡片缺 article:* 四件套

P2 分享到 Slack / Telegram / LinkedIn 看不到日期和作者

文章页当前的 OG 标签实测只有 9 个：

og:title  og:description  og:type  og:url
og:image  og:image:width  og:image:height  og:locale  og:site_name

缺 article:published_time、article:modified_time、 article:author、article:tag。 全站 366 页里这四项出现 0 次。Facebook / LinkedIn / Slack / Telegram 的 unfurl 都会读它们，缺了就只显示一个光秃秃的标题。

数据是现成的——JSON-LD 里已经有 datePublished、dateModified、 author、标签列表，只是没往 OG 里写。改一个文件： layouts/_partials/opengraph.html，在 og:type 后面补四行。

顺带两个同类小缺口：og:image:alt（0 处，图片无障碍读屏要用）、 twitter:site（0 处，有这个才会在卡片上显示 @账号）。

05P2 · 五个根级页的 description 只有一两句话

P2 文章页没问题，独立页偏短

先说结论：文章页的描述是健康的，中位 60 字、均值 61.6， 对中文来说正好是 Google 摘要的舒适区。真正偏短的只有 5 个根级页：

页面description 字数现状
/now/12最短，几乎等于没写
/weekly/25偏短
/roll/33偏短
/run/41偏短
/donate/46偏短

这 5 页里只有 /donate/ 是 noindex， 另外 4 个（/now/、/weekly/、/roll/、/run/） 全部在 sitemap 里、是可索引的落地页，值得各写满 60 字左右。 改的是各页 front matter 的 description，不用动模板。

06P2 · 页面上不显示「更新于」，但数据是有的

P2 长期维护的博客，这个信息对读者有用

JSON-LD 里 dateModified 一直是对的（例如 2026-10-26T11:21:44+08:00），sitemap 的 148 条也全部带 lastmod。 但文章页面上只显示发布日期，读者看不到「这篇最近改过」。

对一个「电子产品清单」这类会过期的文章来说，这个信号挺重要。 做法：在 layouts/_default/single.html 的日期行加一个条件—— dateModified 比 date 晚 1 天以上才显示「更新于 …」， 否则只显示发布日期，避免每篇都挂两个日期。

08不建议做的（免得来回折腾）

这几件事我考虑过，结论是保持现状更好，理由都写在这里，以后不必再评估一遍。

① 给标签页开索引

157 个标签只对应 1 篇文章。开索引等于凭空多 157 个「和文章几乎重复」的薄页面， 只会把 Search Console 的「已抓取 - 尚未编入索引」从 0 撑到三位数。先做第 03 节的标签归并， 等出现 ≥ 10 篇文章的标签，再考虑像分类页那样分级放行。

② 给 /posts/ 加分页 / 无限滚动

107 条全部渲染出来只有 39.8 KB，gzip 后 10.9 KB，一次请求就到位。 加分页会变成 11 次请求，无限滚动还要引入 JS 与滚动监听——纯亏。 /archive/ 同理：133 条 gzip 15.2 KB，是可索引页里最省的一个。

③ 加一个深色/浅色切换按钮

现在跟随系统（prefers-color-scheme），两套配色都完整。加手动切换要处理 首屏闪烁（FOUC）、localStorage 同步、按钮的无障碍标签， 而收益只是「系统是浅色但我想看深色」这一种情况。

④ 把内联 CSS 拆成外部文件

CSS 全内联是既定架构（产物没有 /css/ 目录），首页 gzip 后 CSS 只占 3.4 KB。 拆出去会多一个请求 + 一次往返，在 TTFB 本来就慢的链路上是负优化。

⑤ Service Worker / 离线阅读

博客不需要离线。加了要维护缓存版本号，改版后用户可能看到旧页面—— 这正是首页 Edge 缓存那件事已经踩过的坑。
