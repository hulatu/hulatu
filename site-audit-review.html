2. P0-1 导航在 360px 下不可达

7 个链接连成一串，中间没有可断点

P0 每页

三个可选方案，成本差很多：

  1. 方案 A（推荐）：@media (max-width: 380px) { header nav { display: flex; flex-wrap: wrap; row-gap: 2px } }。约 90 B，390px 以上零变化。折行后第一行是 Home…Posts、第二行只有 RSS，视觉上略孤。
  2. 方案 B：把 RSS 从导航拿掉（页脚已有「Subscribe via RSS」）。6 项 = 301.42px，360px 下装得下，320px 仍溢出 21px。要动内容决策。
  3. 方案 C：≤380px 时导航字号降到 0.85em。351.42 × 0.85 = 298.7px，360px 装下，320px 仍溢出 19px。字变小，与「导航是次要导航」的定位相符。

三个方案都不能单独解决 320px，320px 只能靠折行。

3. P0-2 派生数据靠手动，已经开始漏

两份「离线生成、提交进仓库」的数据，没有跟内容一起更新

P0 正在发生

站点的架构是「构建零网络依赖」，所以两类数据必须离线生成后提交：data/image-dims.json（图片宽高，防 CLS）与 static/images/og/*.png（每篇一张分享卡）。代价写在 render-image.html 的注释里：「加了新图要重跑一次那个脚本」。

问题是这个「记得重跑」没有落点。deploy.sh 里没有它们，publish.sh 里也没有。于是：

派生数据应覆盖实际缺口
分享卡片 og/*.png128 篇127 张newsletter-26（10-18）走兜底图
图片尺寸 image-dims.json325 张323 张VNklE1.jpg（10-16）、DdRKrt.png（10-18）

两处都静默降级：没有卡片就用 share.webp，没有尺寸就不输出 width/height。构建 0 警告，页面上看不出任何异常 —— 只有分享到社交平台、或者图片加载时内容跳一下，才会暴露。

值得注意的是：跑步数据 runs.json 已经自动化了（Garmin 同步脚本 + 自动提交，git log 里能看到 Auto Update: 同步 Garmin 跑步数据）。所以这不是「做不到」，是「这两份没接上」。

改哪儿：deploy.sh（在 hugo 构建前调用两个脚本）或 publish.sh（提交前）
代价：构建时间 +6.5s（gen-og 实测 6536ms）+ 一次图床网络请求（sync-image-dims 要抓图）
⚠️ 注意：deploy.sh 的设计前提是「零网络依赖」，把抓图脚本放进去会破坏这条。更稳的是放 publish.sh，或者做成「有改动才跑」。

4. P1-1 每篇文章有两个 <h1>

页头站名占掉了 h1，文章标题只能并列

P1 134 页

主题的 header.html 只有两行：

<a class="title"><h1>{{ .Site.Title }}</h1></a>

于是每一页的第一个 h1 都是「胡拉图说」。文章页又在 single.html 里输出 <h1>{{ .Title }}</h1> —— 一页两个 h1。

这不违反 HTML 规范（HTML5 允许多个 h1），但两件事会受影响：屏幕阅读器的标题大纲里，每篇文章的主题都排在站名之后、同级；搜索引擎判断「这一页讲什么」时，站名的权重和文章标题一样。

标题大纲 · 现状 vs 改造后同一篇文章

现状：两个 h1 并列

H2 第一次参加团面
H2 奇妙体验
H2 别为了说而说

改造后：站名降为普通文本，文章标题独占 h1

P 胡拉图说 ← 改成 <p class="title">，外观完全不变

H2 别为了说而说

改哪儿：新增站点层 layouts/partials/header.html（覆盖主题同名文件，第 27 个站点层文件），把 <h1> 换成 <p class="title">
连带：首页 / 归档页 / 各列表页会失去唯一的 h1，需要各补一个页面级标题（或接受 0 个 h1）
⚠️ 视觉零变化的前提：主题对 .title h1 的样式要一起搬到 .title p，否则字号会掉

6. P1-3 加载层：两个没花的便宜钱

没有 preconnect，首图也是 lazy

P1

① 图床没有 preconnect。正文图片全部托管在 img.hulatu.com，但 head 里 preconnect / dns-prefetch 的出现次数是 0。实测这个域名的 TLS 握手：

样本DNSTCPTLS总
10.00010.00040.9501.815
20.00020.00100.6111.763
30.00010.00101.7703.378

DNS 是缓存过的，所以慢的纯粹是握手。现在浏览器要等到解析出第一个 <img> 才开始这一步；加一行 <link rel="preconnect"> 能把它挪到 head 解析时并行开始。cf-ray 显示这台机器被路由到 LAX，握手慢是这个原因，不是图床配置问题。

② 325 张图全是 loading="lazy"，0 张 eager。render-image.html 给每个 <img> 无条件加了 lazy，包括文章的第一张图。首屏内的图仍然会被加载（Chrome 的 lazy 阈值是 1250px），但会晚一个 RTT。上一轮清单里的 P1-4 就是这条，你没有点名，所以一行未改。

① 改哪儿：layouts/partials/custom_head.html 加一行 <link rel="preconnect" href="https://img.hulatu.com">（或放在 seo_tags.html）
② 改哪儿：layouts/_default/_markup/render-image.html，用 .Ordinal 或计数器判断第一张，输出 loading="eager" fetchpriority="high"
⚠️ ② 的坑：文章页与列表页共用这个 hook，要确认「第一张」是按页算的
