2. 诊断：三处「界面不说状态」

2.1 导航不标当前页

7 项导航，全站 0 / 337 页输出 aria-current 或任何当前页类名。产物里的导航永远是七个蓝链接：

产物原文 · /about/ 页的 <nav>337 页同形
<a href="/">Home</a><a href="/about/">About</a>…<a href="/index.xml">RSS</a>

这不是「少个装饰」。DESIGN.md:438-446 把「/about/ /now/ /roll/ 三页藏掉页面标题」的理由，明确写成：

「导航里那项 About 已经在指示『你在哪一页』，正文顶上再写一遍『关于』是冗余。」

而实现里没有任何指示。也就是说：这三页现在既没有页面标题，导航也不高亮 —— 用户只能看 URL 判断自己在哪。文档的论据和代码对不上，这是这一轮最值得修的一处。

2.2 键盘用户进不去正文

全站 0 / 337 页有 skip-link。按 Tab 的第一次焦点落在站名链接，要连按 8 次（站名 + 7 项导航）才到正文第一条链接。长文页还有面包屑和目录，实际更多。

WCAG 2.4.1（Bypass Blocks）是 A 级要求 —— 这是「专业」最硬的一条指标，比任何视觉修饰都硬。

2.3 打印时把界面一起印出来

全站 0 / 337 页有 @media print。你写的是研究生博客，文章里有代码块、图表、数据表 —— 存 PDF 或打印的场景是真实存在的。现在按 Cmd+P，会印出：

  • 7 项导航（蓝色，纸上偏淡）
  • 面包屑
  • 右侧目录（position: fixed，在纸上会叠在正文上）
  • 4 行页脚 + 🚇 开往 + 🗺️ Sitemap
  • 返回顶部按钮（固定定位，可能印在最后一页角落）
  • 默认展开的评论区

7. 不建议加（连同理由，免得下次重提）

这一节比上面四节更重要 —— 它决定了「专业」是靠加对的东西，还是靠不加错的东西。

提案裁决依据
text-autospace（中英自动空距） 不做 2026-10-11 实测过：本机 Chromium 155 里连显式 ideograph-alpha 都零效果，五个变体截图逐字节相同。记录在 custom_head.html:120-147。等浏览器升级后按同一方法复核，现在加回去是死声明。
text-spacing-trim / font-feature-settings: "halt" 做不了 Songti SC 与 PingFang SC 都没有 halt / chws 特性，属性会被浏览器静默禁用 —— 写了比不写更糟（下次有人会以为它在起作用）。
阅读进度条 不做 2026-10-11 加过，当天用户要求删（「进度条不要，去掉」）。DESIGN.md:1408 写明「别再提」。
全文搜索面板 不做 2026-10-10 删。列表页已有标题过滤，全文索引要自带一份 JSON + 面板，代价远大于收益。
深浅色手动开关 不做 跟随系统是零配置的正确答案；手动开关要 LocalStorage 记忆，且与「不留状态」的定位冲突。

这一节同样是交付物的一部分。下面这些如果被「优化」掉，站会变差：

  • 单一强调色。#0066cc 只用于链接，全站没有第二个品牌色。这是这个站看起来「安静」的根本原因。
  • 虚线 hr。首页 Hi! 与 Recent Posts: 之间、/roll/ 两组之间，都是裸 <hr> 走主题那一条 1px dashed。别给它加类名或宽度。

  • 目录默认隐形。不悬停只看得见一排灰色短横。DESIGN.md:787-791 写明这是用户明确选的。
  • 零 JS 的返回顶部。纯 CSS 滚动驱动动画，不支持时退回常显。别改成 JS 监听 scroll。
  • 标题末 2 字 nowrap。orphan-safe.html 只动那几条会留孤字的标题，其余零变化。别扩到 3 字。

9. 手机上的长文目录（已拍板：方案 C）

手机上的长文目录

右侧目录在 ≤1200px 整块 display: none（custom_head.html:1482）。这是你 2026-10-12 拍板的「方案 A：干脆不显示，把资源留给正文」—— 当时是对的，因为 1000–1200px 视口下侧栏算出来只有 1–176px，内部却固定要吃 100px，hover 展开后一个字都读不出来。

但代价现在可以量化：127 篇长文在手机上没有任何目录。而手机恰恰是最需要「跳到第 4 节」的场景。这不是「把侧栏搬回来」（物理上做不到），而是一个新形态的选择：

  • 方案 A（现状）：不做。手机靠滚动，长文靠浏览器自带的「查找页内文字」。
  • 方案 B：正文顶部插一个 <details> 折叠目录，只在 ≤1200px 显示，复用 {{ .TableOfContents }}。代价：每页多一份目录 DOM（约 0.5–1.5 KB），且要处理「目录和正文标题重复」的观感。
  • 方案 C：只在「h2 ≥ 3 个」的文章显示折叠目录，短文章不显示。

我倾向 方案 C：它把「多一份 DOM」的成本限制在真正需要跳转的长文上，而且判断条件在模板里就能算（.Fragments.Headings 的长度），不需要 JS。但它会新增一处「按内容决定是否渲染」的逻辑 —— 而这正是 DESIGN.md 反复提醒要小心的那类改动（守卫按页型还是按内容）。所以这件事我不替你决定。

已拍板并实施 · 2026-10-17 · 方案 C

你选了 方案 C，已经落地：正文顶部一个 <details>，只在 ≤1200px 出现 —— 与侧栏共用同一个 1200px 断点，两者正好互补，不会同时出现。

  • 范围：337 页里 55 页输出（h2 ≥ 3）。实测 h2 ≥ 3 漏出 0、h2 < 3 误出 0；h2 分布 3–11。
  • 成本：CSS 每页 +1089 B raw / 约 +720 B gzip；DOM 只在 55 页多一份，最大的一份约 1.4 KB。
  • 零 JS：<details> 原生折叠，点链接走浏览器默认跳转。也刻意不做「点完自动收起」—— 跳转后目录已经滚出视野。
  • 语义：手机版那份换成 <nav aria-label="本页目录">，全页 id="TableOfContents" 仍恰好 1 个（留给侧栏），没有重复 id。

实施时踩到两个坑（都已写进 DESIGN.md 10.3）：

  • .Fragments.Headings 的第一层是 Level = 0 的哨兵根节点，不是 h2 列表 —— 一篇 11 个 h2 的文章，len 出来是 1（结构是 [0:11]）。只遍历第一层判 Level 2 恒等于 0，目录永远不渲染，而构建 0 警告。
  • A4 的 CSS 宽度约 793px，裸的 @media (max-width: 1200px) 在打印时也匹配 → 目录会被印在纸上。改成 @media screen and (...)，并在第 29 段的打印隐藏清单里补了 .toc-mobile。用 --print-to-pdf 转首页 PNG 验过：确实没有目录。
