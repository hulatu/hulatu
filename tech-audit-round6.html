2.5 未使用 CSS 类 P1

CSS 中定义了 280 个类，模板中使用了 190 个， 有 90 个类只在 CSS 中定义、未被任何模板直接引用。

但多数属于正当残留：

  • 代码高亮语法类（.chroma, .c, .c1, .cm…）— Hugo 内置 Chroma 生成，模板不直接写这些类
  • Markdown 生成结构类（.footnotes, .footnote-ref, .footnote-backref）— 由 .Content 渲染时注入
  • 状态类（.is-hidden, .is-open, .is-loaded）— 由 JS 动态添加
  • 页面前缀类（.about-, .archive-, .friends-）— 扫描脚本的误报（实际是 .about-section 等完整类名）
真正可疑的：扫描脚本列出的 .article__section__wrapper、.comp__Directory、 .comp__Directory__overlay、.is-failed、.is-pinned —— 这些类在模板中完全找不到引用， 可能是历史遗留或从未实现的功能。建议手动确认后删除。

3.1 search.js 体积 P1

search.js 16.2 KB 是全站最大的 JS 模块。它包含：

  • Fuse.js 近似搜索逻辑（内联了精简版 fuse）
  • 搜索面板 DOM 操作
  • 键盘快捷键（/ 打开、Esc 关闭）
  • 焦点陷阱（focus-trap）— 但这个功能已经被拆成独立模块 focus-trap.js

检查 search.js 是否仍然内联了 focus-trap 逻辑——如果 focus-trap.js 已经独立， search.js 里的重复代码可以删掉，预计能省 1–2 KB。

3.2 模块合并机会 P2

theme.js（2.2 KB）和 focus-trap.js（2.0 KB）都很小， 但 Hugo 的 js.Build 会把它们各自打包成一个 bundle（加上 runtime 开销）。 如果合并到 ui.js 或 search.js 中，可以减少一次 HTTP 请求和 webpack runtime 重复。 不过收益有限（ Hugo 的 js.Build 已经做了 tree-shaking）。

4.1 最大 Partial：css-modules.html P2

css-modules.html 148 行，是全站最大的 partial。它负责根据页面类型选择加载哪些 CSS 模块。 虽然逻辑复杂是正当的（6 个模块 × 4 种页面类型 = 24 种组合判断），但 148 行对于一个「路由表」来说偏长。 可以考虑把条件判断压缩成一张 lookup table，把行数压到 50 行以内。

4.2 head-meta.html P2

head-meta.html 109 行，包含 SEO、Open Graph、Twitter Card、结构化数据等。 其中 Twitter Card 和 Open Graph 有大量重复属性（og:title 和 twitter:title 值相同）。 如果 Twitter 已经能读 Open Graph（实际上从 2023 年起 Twitter 就优先读 og:*）， 可以删掉 Twitter Card 的重复标签，省 10–15 行。

5.1 icon-512.png 压缩 P1

512×512 PNG 29.7 KB 对于纯色/简单图形来说偏大。用 oxipng 或 pngquant 可以压到 10 KB 以下。 如果图标是简单的文字/图形，转成 SVG 或更激进的 PNG 压缩收益很大。

5.2 avatar.webp 引用检查 P1

扫描显示 avatar.webp 未被任何模板或 Markdown 文件引用。它可能在 CSS 中被引用（background-image）， 需要确认。如果确实未使用，可以删除，省 17.4 KB。

5.3 PWA 完善 P1

八、需要拍板的问题

Q1：Twitter Card 还要保留吗？
从 2023 年起 Twitter（X）已经优先读取 Open Graph 标签，twitter:* 标签不再是必需的。 删除它们每页可以少 5–8 个 <meta> 标签，但会失去对旧版 Twitter 客户端的兼容。 你的决定是？
Q2：Service Worker 要做吗？
加一个简单的 SW 可以让博客在断网时阅读已访问过的文章， 但第一次部署后如果 SW 有 bug，用户可能需要手动清除缓存才能更新。 你的决定是？
Q3：CSS 模块要合并吗？
当前 6 个 CSS 模块（critical / critical-post / critical-page / critical-info / core / post） 按页面类型条件加载，逻辑清晰但文件多。合并成 3 个（critical-all / core / post）可以减少 HTTP 请求， 但会让「文章页」多加载一些「关于页」才用的规则（反之亦然）。 你的决定是？
