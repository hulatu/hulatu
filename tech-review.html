03P0 · 图片是唯一的大头

这是全站唯一一处「代价明显、而且现成能力没用上」的地方。我抽样测了 14 张图，又完整测了一篇 21 图的周刊。

现状：八处同时没做

事实实测
全站图片342 张，全部来自 img.hulatu.com
响应式图片srcset = 0，每张只有 1 个固定 URL
抽样平均体积94.7 KB（14 张抽样，最大 220 KB）
最重的一篇《周刊 10》21 张图 = 1.74 MB

最要紧的一条

那个 .webp 其实是 JPEG —— 说明当初「转格式」只改了文件名，没真的转码。所以这 73 张一点压缩收益都没拿到，反而让「站里已经是 WebP 了」这个判断失真。

好消息：图床本身就有边缘转换能力

图床响应里带着 cf-resized 头 —— 它跑在 Cloudflare 的图片处理链路上。我直接试了标准的 /cdn-cgi/image/ 前缀，是可用的：

# 原图
https://img.hulatu.com/post/UHYgCr.jpeg                       111 KB

# 加边缘转换（宽度 720、自动选格式、质量 80）
https://img.hulatu.com/cdn-cgi/image/width=720,format=auto,quality=80/post/UHYgCr.jpeg
                                                              46 KB  (省 59%)

批量验证 4 张，加上完整测了一篇周刊：

4 张抽样省 47–71%，整篇省 51%。而且手机端还能再降一档 —— 400px 的 AVIF 版本只要原图的 14–20%。

怎么改：只动 render-image.html 一个文件

不需要跑脚本、不需要重新上传图片、不需要改图床配置。URL 前缀是现成的，模板里拼一下就行：

{{- $u := .Destination -}}
{{- $isHosted := strings.HasPrefix $u "https://img.hulatu.com/" -}}
{{- $base := $u -}}
{{- $srcset := "" -}}
{{- if $isHosted -}}
  {{- $path := strings.TrimPrefix "https://img.hulatu.com/" $u -}}
  {{- $mk := "https://img.hulatu.com/cdn-cgi/image/width=%d,format=auto,quality=80/%s" -}}
  {{- $srcset = printf "%s 400w, %s 720w, %s 1080w"
        (printf $mk 400 $path) (printf $mk 720 $path) (printf $mk 1080 $path) -}}
  {{- $base = printf $mk 720 $path -}}
{{- end -}}

<img src="{{ $base }}" srcset="{{ $srcset }}"
     sizes="(max-width: 760px) 100vw, 720px" ...>

三件事要一起做，缺一个收益都会打折：

  1. srcset + sizes —— 让手机拿 400w、桌面拿 720w，而不是所有人下同一张。
  2. 首图加 fetchpriority="high" —— 其余保持 lazy。现在的做法是 340 张全 lazy，连首屏那张也要等布局算完才开始下。
  3. 给 img.hulatu.com 加 preconnect —— 现在 preconnect 只给了 giscus，等于把最慢的那个连接（实测 TLS 0.63–0.86 s、首字节 1.6–2.1 s）留到最后才建。
还能顺手做的一件事

图床那边补一条 Cache-Control: public, max-age=31536000, immutable。文件名都带随机后缀（UHYgCr 这种），内容实际不可变，现在却是「无缓存头」状态 —— 浏览器每次都要重新问一遍。这条在 Cloudflare 后台或用 R2 的自定义头都能加，跟代码无关。

这个比图片更影响「博客作为一个整体」的价值，但修起来是纯模板工作。

现在文章页底部的出口只有三种：按日期排的上一篇/下一篇、系列带（只对 series: 生效）、评论区。也就是说，一个读者从搜索结果落到《苹果 App 推荐》之后，下一篇大概率是「碰巧日期相邻」的文章，而不是「同样聊 Mac 效率」的那篇。

而站上已经有 206 个标签、9 个分类，这些数据完全可以驱动推荐，只是从来没被用来做推荐。

建议：用 Hugo 内置的 .Related

{{- $rel := site.RegularPages.Related . | first 4 -}}
{{- with $rel }}
<nav class="post-related" aria-label="相关文章">
  <h2>相关文章</h2>
  <ul>
  {{- range . }}
    <li><a href="{{ .RelPermalink }}">{{ .Title }}</a>
        <span class="post-related-date">{{ .Date.Format "2006-01-02" }}</span></li>
  {{- end }}
  </ul>
</nav>
{{- end }}

再在 hugo.toml 里给个权重（标签比日期重要得多）：

[related]
  threshold = 20
  includeNewer = true
  toLower = false

  [[related.indices]]
    name = "tags"
    weight = 100

  [[related.indices]]
    name = "categories"
    weight = 50

这一块是纯静态生成的，0 请求、0 JS、构建时算完，不会给现在这套「零外部依赖」的架构添任何负担。成本就是每页多几百字节 HTML。

顺带一个副产品

一旦有了「相关文章」，标签碎片化的问题会自动缓解 —— 因为标签的价值从「给读者点进去看列表」变成了「喂给推荐算法」，206 个标签不再需要每个都撑起一个像样的列表页。

好消息

你已经把标签页设成了 noindex, follow，sitemap 也排除了 tags / categories（实测 sitemap 里 tags 计数 = 0）。所以这个问题没有在伤害 SEO —— 它纯粹是「站内发现性」和「维护成本」的问题。这也是为什么它排在图片和互链后面。

处理思路不需要大动干戈，两条就够：

  1. 合并同义：跑步 / 运动、AI / 人工智能、Mac / macOS 这类先归一。
  2. 只保留「≥2 篇」的标签：单次标签降级成正文关键词，不进 tags:。206 → 大约 56 个，每个都撑得起一个列表页。

06P1 · 首页还是被边缘缓存压着

这个问题上次就报过，现在依然存在，而且症状没变：

$ curl -sI https://hulatu.com/
cache-control: public, max-age=0, must-revalidate   ← 源站说的是「别缓存」
cf-cache-status: HIT                                ← 边缘说「我缓存了」
age: 2633                                           ← 44 分钟前那份

其它页面（/posts/、/archive/、/feed/）都是 DYNAMIC，只有首页 / 被单独锁住。这说明后台有一条 Cache Rule 或 Edge TTL 专门覆盖了 /，而 static/_headers 里的 must-revalidate 管不到它。

为什么必须处理

这意味着你每次改 CSS 或首页文案，访客都可能要等几十分钟才看到。上次改站名颜色、改图标，本地和源站都对了，只有访客看到的还是旧版 —— 排查了半天才发现是这一层。根治只有一条：Cloudflare 后台 → Caching → Cache Rules，给 HTML 设 Edge TTL = 0（或直接排除 text/html）。

07P2 · 零碎但该修的

项现状与建议
归档页搜索框 产物是 <input id=search-input type=text placeholder=搜索标题…>。没有 label、没有 aria-label，屏幕阅读器只会念「编辑框」。建议：type="search" + aria-label="按标题筛选文章" + 去掉内联 style。
layouts/.DS_Store 又出现了（上次删过 9 个）。它会让「站点层文件数」多算一个，而且每次在 Finder 里翻目录都会再生。建议加进 .gitignore 一劳永逸。
8 篇摘要过短 最短 33 字（/roll/）、42 字（周刊 3）、44 字（周刊 1）。这些是列表页和搜索结果里的门面，建议补到 60–80 字。
1 张图空 alt embrace-english 里那张 jIBUDw.webp 的 Markdown 是 ![](...)，产物 alt 为空。配图建议补一句描述。
350 处拼音锚点 {#ti-qian} 这类显式 id 由 add-heading-anchors.py 自动加，slugify 只取前 6 段，所以会出现半截拼音。方案 A/B/C 你之前还没选 —— 不影响功能，只是 URL 里 #ti-qian 不太好看。

09不建议动的

有些地方看着「不够现代」，但现在这样是对的，改了会更慢或更复杂：

  • CSS 全内联（11.5 KB） —— 换来 0 个额外请求。对 359 页的静态站，这比抽成外部文件更快（省一次往返），而且 HTTP/2 时代请求数已经不是瓶颈，往返次数才是。
  • 纯系统字体 —— 0 个字体文件、0 FOIT/FOUT。中文 Web 字体动辄 2–5 MB，用系统字体是这里最正确的决定。
  • checkbox 实现的图片放大 —— 0 行 JS 换一个完整 Modal，还自带键盘可达性（:focus-visible 有样式）。换成 JS 库只会更重。
  • 构建零网络依赖 —— 图片尺寸走 image-dims.json 而不是 resources.GetRemote，是对的。上面建议的边缘转换也是运行时拼 URL，不碰构建期，所以这条底线不受影响。

10如果只做三件事

  1. 图片管线（P0）—— 改 render-image.html + 加 preconnect + 首图 fetchpriority。一次改动，全站 340 张图受益，实测省一半流量。
  2. 相关文章（P1）—— single.html 加一个 .Related 块，把 206 个标签从「装饰」变成「推荐燃料」。
  3. 关掉首页的 Edge 缓存（P1）—— 后台一条 Cache Rule。不做这个，前两条改完你自己都看不到效果。

剩下的（标签合并、搜索框无障碍、.DS_Store、摘要补字）都是「顺手」级别，可以攒到下一次批量整理时一起做。
