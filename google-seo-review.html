Technical SEO Audit

Google 收录审查

对 hulatu.com 的抓取、索引、结构化数据与站内链接做一次全量实测。 结论先行：技术层几乎没有错误，真正影响收录的是结构—— 全站没有可索引的主题聚合页，且正文几乎不做站内互链。

审查时间 2026-10-26 构建 Hugo 370 页 / 366 HTML / 0 警告 可索引 140 页 noindex 226 页

01结论

先说最重要的一句：你在 Search Console 里看到的大部分「异常」不是故障。 本站有 226 个页面带 noindex（212 个标签页、8 个分类页、/posts/、 /privacy/、/donate/、两个 feed 视图、404），它们会稳定地出现在 「已排除」里。这是设计意图，不是问题。

实测下来，技术层是干净的：

所以下面只谈三件真正能改变收录结果的事，按影响排序。

02P1 · 分类页全部 noindex，全站没有主题聚合页

P1 唯一的「主题枢纽」被自己关掉了

8 个分类页的实测文章数：

分类文章数当前状态
思考38noindex, follow，不在 sitemap
周刊27noindex, follow，不在 sitemap
工具19noindex, follow，不在 sitemap
记录18noindex, follow，不在 sitemap
运动12noindex, follow，不在 sitemap
学习科研10noindex, follow，不在 sitemap
饮食5noindex, follow，不在 sitemap
健康4noindex, follow，不在 sitemap

后果有三层：

  1. 没有可排名的落地页。「工具」「思考」这类词本来可以由分类页承接， 现在 Google 手上只有 133 篇单文，没有一个「某主题下全部文章」的入口。
  2. 权重只能汇到一个点。唯一可索引的列表页是 /archive/， 它把 133 篇平铺成一条时间线，没有主题语义。所有内链权重都流向它，无法按主题分流。
  3. 标签页顶不上。212 个标签页里 158 个（74%）只对应 1 篇文章， 单个标签页和那篇文章本身几乎同构，做不了聚合。

建议：按文章数分级放行

≥ 10 篇的 5 个分类改为可索引，< 10 篇的 3 个维持 noindex。 阈值取 10 的理由是：低于 10 篇的分类页内容量接近单篇文章的目录，容易被判 「已抓取 - 尚未编入索引」，反而多一条负面记录。

判定逻辑在 layouts/_default/baseof.html 第 31 行，当前是「分类一律 noindex」：

{{- $noindex := or (eq .Data.Plural "tags") (eq .Data.Plural "categories")
                    (eq .Kind "404") (eq .Params.noindex true) -}}

改成：

{{- $noindex := or (eq .Data.Plural "tags") (eq .Kind "404") (eq .Params.noindex true) -}}
{{- if and (eq .Data.Plural "categories") (lt (len .Pages) 10) -}}
  {{- $noindex = true -}}
{{- end -}}
⚠️ 这个改动必须同时改两个文件。 layouts/sitemap.xml 里有一份逐字相同的 $noindex 判定， 两处一旦漂移，构建 0 警告、页面照常生成，唯一症状是「sitemap 里又混进了 noindex 页」。 文件注释里已经写了这条警告，但靠人记不可靠 —— 见下一节的根治办法。

配套：给这 5 个分类页写 description

分类页目前复用站点描述（实测 225 个页面共用同一句）。放行后必须各自有摘要， 否则会变成「同标题同描述的一批列表页」。新增 5 个文件即可： 

content/categories/思考/_index.md
---
title: "思考"
description: "关于选择、习惯与长期主义的 38 篇记录。"
---

03P2 · 两处结构化数据缺口

P2 JSON-LD 的 image 全站共用一张图

实测：133 篇文章的 JSON-LD 里，image 取值集合只有一个元素。

抽样 40 篇，JSON-LD image 取值集合:
{('https://hulatu.com/images/share.webp',)}

但同一批页面的 og:image 是每篇独立的： /images/og/apple-app-recommendations.png 这种，133 张全部存在、全部 1200×630。

为什么这是问题：Google 的 Article 富媒体结果与 Discover 读的是 JSON-LD，不是 og:image。现在 133 篇文章在 Google 眼里 共用一张通用图，等于放弃了逐篇缩略图的差异化。

修法很轻：layouts/partials/seo_tags.html 里现在是这样取图的 —— 

{{- $img := "" -}}
{{- with .Site.Params.images -}}
  {{- $img = index . 0 -}}
{{- end -}}

改成与 layouts/_partials/opengraph.html 同一套逻辑即可（那段已经验证过）：

{{- $img := "" -}}
{{- if and .IsPage (in (slice "posts" "weekly") .Type) -}}
  {{- $rel := printf "images/og/%s.png" .Slug -}}
  {{- if fileExists (printf "static/%s" $rel) -}}
    {{- $img = $rel | absURL -}}
  {{- end -}}
{{- end -}}
{{- if not $img -}}
  {{- with .Site.Params.images -}}{{- $img = index . 0 | absURL -}}{{- end -}}
{{- end -}}
注意：这里用了 fileExists，查的是磁盘上的 static/...，不是 URL。漏写 static/ 会永远返回 false， 症状是「图生成了但页面仍用兜底图」，而且构建 0 警告。

P2 article:* 系列 OG 标签全站为 0

og:type 已经是 article，但配套的四项一个都没有：

标签现状影响
article:published_time全站 0 处微信 / 聚合器 / 部分阅读器取不到发布时间
article:modified_time全站 0 处同上，且无法体现「已更新」
article:author全站 0 处作者归属信号缺失
article:section / article:tag全站 0 处主题分类信号缺失

根因是站点层覆盖了 layouts/_partials/opengraph.html，而那份覆盖只输出了 7 个字段，没有跟着 Hugo 内置模板输出 article:*。

优先级说明：Google 的收录不依赖这四项（日期以 JSON-LD 为准， 已确认 datePublished 正确输出为 ISO 8601）。所以这是「顺手补齐」级别， 不是收录障碍。

实测（只统计正文里指向站内的 Markdown 链接，不含图片、不含锚点）：

指标数值

先澄清一个容易误判的点：这不影响抓取。每篇文章的入链最低 7 次、 中位 13 次（靠 /posts/、/weekly/、/archive/ 三个列表页）， 全部 2 跳可达。

它影响的是相关性：站内链接是主题信号的主要通道。现在 133 篇文章之间 唯一的关联是「同标签」，而 74% 的标签只对应 1 篇文章 —— 等于绝大多数文章之间 没有任何主题关联，只能靠 .post-related 的算法推荐兜底。

这是纯内容活，没有代码可改。成本最低的做法：每周挑 5 篇旧文，各补 1–2 条指向相关旧文的正文链接。

标签页全部 noindex，所以不伤 SEO。但两个副作用是真的：

  • 抓取预算。212 个 noindex 标签页，每篇正文底部链出 5–8 个 → 爬虫每次都要多抓 200 多个「读了也不收录」的页面。

05需要你去 Search Console 确认的四件事

有几件事在站点外部，我无法从代码侧判定。按重要性排列：

① 抓取统计信息 → Googlebot 拿到的 HTTP 状态码

这一条最值得先看。我实测发现本站对非浏览器 UA 有拦截行为： 

curl 默认 UA  → https://hulatu.com/posts/.../  → 403
Googlebot UA  → 同一地址                      → 无响应（000）

这两个结果不能直接推出「Googlebot 被拦」——Cloudflare 会按反向 DNS 校验伪造的 Googlebot，我用普通 IP 冒充必然失败。但它说明站前确实存在 UA 维度的访问控制。

去 GSC 看「设置 → 抓取统计信息 → 按响应」：如果出现 403 或 5xx 的明显占比， 就是 Cloudflare 的 Bot Fight Mode / WAF 在拦真实爬虫，这会导致大面积不收录， 必须立刻在 Cloudflare 后台放行 Verified Bots。

② 网页编入索引 → 已排除清单

预期会看到（这些都是正常的）：

原因预期条数是否要处理
已提交但被 noindex 排除 / noindex226否，设计意图
网页会自动重定向2否（/tags/ /categories/ → /archive/）
已抓取 - 尚未编入索引?要，见下
已发现 - 尚未编入索引?要，见下

后两项如果数量超过 10，且落在正文文章上，说明内容被判为低价值或重复。 本站正文中位数 2294 字、最短 348 字，只有 2 篇低于 500 字 （《剪辑生活Vlog》348 字、《假期余额归零，我已到校》411 字），不构成批量问题。

③ 网址检查：抽 3 篇看实际状态

建议抽最新的、最老的、以及一篇周刊。若显示「已抓取 - 尚未编入索引」， 说明 Google 认可抓取但不认可价值 —— 那就回到第 4 节（内链 + 标签合并）。

④ 增强功能 → 文章

本站 BlogPosting 的必填四项（headline / image / datePublished / author）实测齐全，应当显示为「有效」。 如果这里报错，先看 image 是否被拒（当前是 share.webp）。

06不建议改的三处

避免过度优化，这三点我实测后认为不该动：

项现状为什么不改
/posts/ 是 noindex 正文页，且不在 sitemap 它与 /archive/ 的 133 条链接100% 重叠， 导航也不链它。让它 noindex 正好避免两个近重复列表页。已核对：sitemap 里确实没有它。
/tags/ /categories/ 返回 301 → /archive/ 这两个索引页被 disableKinds = ["taxonomy"] 关掉了。 301 比 404 好（保留任何历史外链的权重），且它们不在 sitemap、不被链接。
CSS 全内联（18 KB / 页） 每页都带完整样式 这是刻意取舍。首屏无额外请求，gzip 后整页中位数 12 KB，实测不是瓶颈。

附带一个不影响收录、但值得知道的事实：static/images/share.webp 的实际字节是 JPEG（服务端返回 image/jpeg）。文件名与内容不一致， 但 Google 与社交平台都按内容嗅探，不影响展示。
