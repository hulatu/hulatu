设计 / 性能评审 · 2026-10-27

还能更现代，但不是靠换皮

站点的外观和加载都已经过了「及格线」很远。真正剩下的问题只有 7 处，其中 2 处值得先做 —— 而它们恰好都不需要动视觉身份。

基线：hugo 0.168.0 · 257 页 · 252 HTML · 0 警告 ｜ 站点层 35 文件 ｜ 全部数字为本轮实测（Helium 无头浏览器读计算样式 + curl 线上探测）

结论 1 加载的瓶颈不在代码，在网络路径。 首页只有 6.0 KB（gzip）、1 个 HTTP 请求、零阻塞资源、零字体外链 —— 这份成绩单已经超过绝大多数个人博客。但 HTML 是 cf-cache-status: DYNAMIC，每次导航都要跨太平洋回源，实测 TTFB 2.0–9.1 秒。
结论 2 外观上「不现代」的地方只有一处是显眼的：搜索框。 它是全站唯一一个完全没有被设计过的控件 —— 实测 174×24 px、border: 2px inset、border-radius: 0，是浏览器 1998 年的默认长相。
结论 3 其余都是「2005 年的 CSS 写法」层面的，不是审美层面的。 段间距小于行距、::selection 未定义、深色模式图片不压亮度、日期字号硬编码。这些改动都看不见「换了风格」，但会让页面显得是被认真做过的。

0 · 先把「现代化」在这个站定义清楚

2026-10-10 你做过一次明确的选择：完全照 Bear Neo，功能也删干净。那之后视觉体系就是上游的 —— Verdana、720px 单列、虚线 hr、链接蓝 #0066cc、全站唯一一档 4px 圆角、没有投影。上一套「纸账 + 印章」已在 DESIGN.md 第 1 节里被标注整体作废。

所以这份评审的立场是：现代化 = 把 2005 年的 CSS 写法升级到 2026 年的浏览器能力，视觉身份一个像素都不动。

它不意味着下面这些（这些是「伪现代化」，而且和你已经做过的决定冲突）：

  • 大圆角卡片、多层投影、玻璃拟态、渐变 —— 与「1px 发丝线 + 空白承担层级」直接冲突，第 6 节里每一条都写了删它的理由。
  • 引入外部 Web 字体 —— 是刻意的设计决策（零外链），而且在 TTFB 已经 2 秒的链路上再加一个域名的 DNS + TLS，是负收益。
  • 前端框架、动画库、图标字体 —— 当前全站外链 JS 只有 2 个文件（1.1 KB + 2.2 KB），没有可优化的余地，只有可破坏的空间。
  • text-wrap: balance / pretty —— 设计目标是英文，在中文里表现为「行提前换行」，正是你会立刻察觉的那种坏。已验证，别再试。
  • 深浅色手动开关、阅读进度条 —— 你分别在 2026-10-11 和 2026-10-17 明确否掉过。

1 · 基线：现在到底有多快

先把「已经做到了什么」摊开。这一步是必要的 —— 因为如果不先确认这些，任何「优化加载」的建议都会撞在已经做完的事情上。

指标实测判断

归档页（133 条） 58,792 B / gzip 14,603 B 优
最长文章页 58,689 B / gzip 19,067 B 优

口径：体积 = 构建产物 --minify 后的字节数，gzip 用 gzip.compress(d, 9)。
TTFB = curl -w %{time_starttransfer}，三次采样加 ?cb= 绕缓存。
为什么是 9 秒：不是站点慢，是「本机 → 洛杉矶 → 源站」这条路上的一次往返。同一个站在东京测只要 48.7 ms —— 这个数字 2026-10 就量过，结论没变。

换句话说得更直白一点：这个站已经把「页面本身」优化到了没什么可优化的地步，剩下 100% 的等待都花在「把 6 KB 送到你面前」这件事上。所以下面关于加载的两条建议，一条都不涉及减小体积。

2 · 外观：三处「没有设计过」的地方

P0搜索框：全站唯一一个浏览器默认控件

它在 /archive/、/posts/、/weekly/ 三个主列表页的顶部。实测计算样式：

属性实测值问题
width174 px（固定）392 px 视口下只占内容宽 352 的一半
height24 px触控目标下限是 44 px
border2px inset rgb(118,118,118)3D 内阴影边框，与全站 1px 发丝线冲突
border-radius0全站唯一一档圆角是 4px
appearanceauto完全没有被接管
font-size16 px合格（≥16px 才不会触发 iOS 聚焦缩放）

改造后取值依据：宽度 100%（跟随 720px 内容列）；高度 44px（与全站触控目标一致）；边框 1px solid var(--border-color)（与图片、表格、代码块同一条线）；圆角 4px（style.html:132/156/191 全站唯一一档）；放大镜用两个伪元素画，不引入图标字体。
落点：layouts/partials/custom_head.html 新增一段，用 #search-input 守卫（这个 id 只在列表页存在，天然按页生效）。
为什么这条是 P0：它是三个主入口页上最显眼的元素，而且它「没被设计过」这件事本身会被读者读成「这个站没做完」。

P0段间距小于行距：长文的段落边界是失效的

实测：正文 line-height: 28.8px（16 px × 1.8），段落 margin: 16px 0。

段间距只有行距的 55.6%。这意味着「换段」在视觉上比「换行」还紧 —— 读者要靠标点和语义去猜段落在哪结束。中文是方块字、没有 x-height 提供节奏，这个问题比英文严重得多。你当初把行高从上游的 1.6 抬到 1.8，解决的是「行内太挤」；段落之间这一层其实一直没跟上。

为什么是 1.75em 而不是 1.5em：1.5em = 24 px 仍小于行距 28.8 px，段落边界还是比行边界紧；1.75em = 28 px 恰好与行距齐平，是「换段 ≥ 换行」的最小值。Apple 中文站与少数派的正文段落都在这个区间。
落点：custom_head.html 第 02 段（那一段已经在管标题上下间距，段落间距属于同一类问题）。写法必须是 content p { margin: 1.75em 0 } 而不是给 content > * + * 加 margin-top —— 后者会和已有的 p 边距叠加成双倍。
代价：一篇 20 段的文章会变长约 240 px（约 5–8%）。这是需要你接受的视觉变化，也是本文里唯一一条会明显改变页面长度的改动。

P1深色模式下，图片比页面亮 6 倍

实测一张普通户外照片在深色主题下的表现：图片区域平均亮度 0.427，页面底色 0.071 —— 差 6 倍。加上图片的边框是 #30363d（在 #121212 上几乎不可见），整块图没有任何过渡地贴在深色底上。

这不是新提案，是找回丢掉的东西：旧主题的 critical-post.css 里有一条 [data-theme="dark"] .article-image img { filter: brightness(.88) }，2026-10-10 迁移到上游主题时随整套 CSS 一起消失了。
落点：custom_head.html 新增一段，@media (prefers-color-scheme: dark) { content img { filter: brightness(.82) } }。
两个必须确认的点：① filter 会创建新的包含块，要和第 21 段的 img { height: auto } 一起验（不会冲突，但要验）；② 灯箱是 CSS-only 的 :checked ~ 方案，filter 挂在 content img 上时放大的那张图也会被压暗 —— 这是期望行为，深色下放大看图不该突然变亮。

P1三处「浏览器默认」没被接管

这三条单独看都很小，但它们是同一个问题：页面里还有一小块区域是「系统的」，不是「这个站的」。

属性实测表现
::selection 未定义（透明） 选中文字是浏览器默认淡蓝，与链接蓝撞色，深色下也不跟
accent-color 未声明 任务清单的 <input type=checkbox> 用 UA 默认蓝，不跟 --link-color
scrollbar-gutter auto 归档页 14.6 KB / 短文页 6 KB，滚动条出现与消失时内容横移 15 px 
/* 三行，都放在 custom_head.html 全站生效的段里 */
::selection { background: color-mix(in srgb, var(--link-color) 22%, transparent); }
:root { accent-color: var(--link-color); scrollbar-gutter: stable; }

color-mix() 而不是写死色值：深色下 --link-color 是 #6da6ff，同一行代码自动跟着走，不用再维护一份深色覆盖 —— 这是这个站「深色只覆盖 8 个颜色变量」的既有做法的自然延伸。
scrollbar-gutter: stable 的代价：页面右侧会永久留出 15 px。在本站这种单列居中布局里几乎看不出来，但它是「所有页面宽度一致」的前提。

P2日期字号硬编码 15px

style.html:184 是 time { font-size: 15px } —— 硬编码 px，不跟随 --font-size-primary: 1em。后果是：用户在浏览器里把默认字号调到 130%，正文变成 20.8 px，日期还是 15 px。同一行里两个字号不再成比例。

改成 font-size: .9375em（= 15/16）即可，视觉在默认字号下逐像素不变。这属于「可访问性修补」，优先级低但成本几乎为零。

3 · 加载：唯一的瓶颈，和两个解

前面那张表已经说明：体积、请求数、阻塞资源、字体、第三方脚本 —— 全部已经做到位了。剩下的一处，也是唯一的一处，是 HTML 不进边缘缓存。

$ curl -sSI "https://hulatu.com/about/" | grep -E "cf-cache-status|cache-control|cf-ray"
cache-control: public, max-age=0, must-revalidate
cf-cache-status: DYNAMIC          ← 没有命中边缘缓存
cf-ray: a511ea2f5a6bf7c1-LAX      ← 落在洛杉矶

DYNAMIC 意味着每一个页面请求都要走完整的回源链路。而 Cloudflare 免费版的 anycast 会把中国流量大量丢到美东 / 美西 / 欧洲 —— 这一点 2026-10 就量过（22 次采样亚洲 0 次），今天的 cf-ray 仍然是 LAX。

P0给 HTML 一个短的边缘缓存 TTL

现在的 static/_headers 里，所有 HTML 规则都是 max-age=0, must-revalidate。这是为了让「发了新文章立刻能看到」，代价是每次访问都回源。但这个代价换来的收益其实被高估了：

改法：static/_headers 里 HTML 那几条从 public, max-age=0, must-revalidate 改成 public, max-age=0, s-maxage=300, must-revalidate。max-age=0 保留（浏览器仍然每次条件请求），s-maxage 只管 CDN 那一层。
代价：发新文章后，最多 5 分钟内部分访客仍看到旧列表页。文章页本身的 URL 是新的，不受影响 —— 受影响的只有首页、/archive/、/posts/ 这几页。
为什么值得：个人博客不是新闻站，5 分钟的可见延迟换「第 2 次访问起快 40 倍」，这笔账是正的。但这一条需要你拍板，因为它和你 2026-10 定下的「发完立刻可见」直接冲突。
注意：_headers 的 s-maxage 会被后台的 Cache Rule / Edge TTL 覆盖。改完必须在 Cloudflare 后台确认一遍，并用 bash scripts/check-cache.sh 复核。

P1补 Speculation Rules：让站内跳转变成 0 ms

全站 0 处。但有意思的是 —— custom_head.html:2600 里已经有这段：

if (document.prerendering) {
  document.addEventListener("prerenderingchange", schedule, { once: true });
} else {
  schedule();
}

也就是说 GoatCounter 那段代码已经为预渲染做好了准备，只是从来没有东西会预渲染它。这条规则被考虑过，但没落地。

<script type="speculationrules">
{"prerender":[{"where":{"and":[
  {"href_matches":"/*"},
  {"not":{"href_matches":"/index.xml"}},
  {"not":{"href_matches":"/index.json"}}
]},"eagerness":"moderate"}]}
</script>

安全性我逐条查过了，这是这次评审里唯一一个「加之前必须先证明安全」的项：

风险点核查结果
写入 localStorage / sessionStorage全仓 0 处
GoatCounter 重复计数已有 document.prerendering 守卫
giscus 重复注入点击展开才注入脚本，预渲染副本不会展开
搜索索引重复 fetch聚焦才 fetch，预渲染副本不会被聚焦
主题 toc.js 副作用只改 class，幂等

eagerness: moderate = 悬停 200 ms 或按下鼠标时开始预渲染。conservative 太保守（只在 pointerdown 时启动，来不及），immediate 会预渲染所有可见链接（在列表页上是 133 个，太过）。
排除 /index.xml 和 /index.json：前者是 RSS 订阅源，后者是 1.03 MB 的搜索索引（gzip 442 KB）—— 预渲染它们没有意义，只会白占内存。
收益：配合上面那条边缘缓存，站内跳转从「2 秒白屏」变成「瞬时」。这一条不解决 TTFB，它解决的是「感知到的等待」—— 把等待从「点击之后」挪到「悬停之时」，而悬停时用户并没有在等。
落点：layouts/_default/baseof.html 的 </head> 前（一行），或 custom_head.html 新增一段。

5 · 要保留的（别在下一轮当问题报）

  • 导航全部用链接蓝。这是 2026-10-17 定下的三态方案：普通蓝 / 悬停蓝+下划线 / 当前页主文字色。custom_head.html:124-143 写明了为什么不能加下划线、不能改字重、不能加底色 —— 每一条都有实测依据（改字重会让 392px 下的 7 项导航折行）。
  • Verdana + 720px + 虚线 hr。这是 Bear Neo 的身份，也是你 2026-10-10 主动选的。它不「过时」，它只是「不流行」。
  • 零外链字体。在 TTFB 2 秒的链路上，再加一个域名的 DNS + TLS 是负收益。
  • CSS 全内联。每页 3.9–4.8 KB（gzip），换成一个外链文件反而多一次往返。
  • text-wrap: wrap（默认值）。中文里 balance / pretty 会让行提前换行，已验证。
  • 深色没有手动开关。跟随系统是零配置的正确答案。

6 · 需要你拍板的三件事

① HTML 边缘缓存：接受 5 分钟的可见延迟吗？

这是三条里收益最大的一条（TTFB 2 000 ms → 约 50 ms，且只影响首页和列表页），也是唯一一条会改变你既有决定的 —— 你 2026-10 特意把 Edge TTL 设成 0，就是为了「发完立刻可见」。

可选：300 秒 / 60 秒 / 维持现状。

② 段间距从 16px 加到 1.75em（28px）吗？

这会让你所有已发布的文章变长 5–8%。排版上更易读，但页面总长度会变。

可选：1.75em / 1.5em（24px，折中）/ 维持 16px。

③ 搜索框改造成「有设计的控件」吗？

这是本文里唯一会新增视觉元素的改动。改完它会成为全站第一个有边框、有圆角、有内边距的输入控件 —— 和其他部分仍然协调（用的是同一套 token），但确实「多了一个设计过的部件」。

可选：完整改造 / 只改尺寸不改外观（44px 高 + 100% 宽，保留系统边框）/ 维持现状。

评审方法：hugo --gc --minify --destination /tmp/modern-site 干净构建（257 页 / 0 警告）； 计算样式用 Helium 无头浏览器（--headless=new --no-sandbox）注入探针读取， 视口 992 px 与 392 px 各测一次；线上用 curl -w 三次采样。
本页所有 mockup 都是手写 HTML/CSS，不是截图 —— 每个值都在注释里标了出处，改的时候照着改就行。
