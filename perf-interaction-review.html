一、真实缺陷（建议修）

1. 图片加载失败时永远不可见 —— 连 alt 文字都看不见 P1

assets/js/ui.js:154-163 · assets/css/critical-post.css:826-830

图片的淡入是这么做的：CSS 先把它压成透明，等 JS 收到 load 再加 is-loaded 放出来 ——

.js .article-image img { opacity: 0; transition: opacity .4s ease }
.js .article-image img.is-loaded { opacity: 1 }

而 ui.js 里只监听了 load，没有监听 error。 于是图床抖动、图片被删、或者任何一次请求失败时，这张图会永久停在 opacity: 0。

后果不只是「少一张图」：读者看到的是 .article-image 那块 --surface-2 的空白灰底框，而 alt 文字长在那个透明的 <img> 里 —— 所以连「这是什么图」的提示都没有。属于静默丢内容。

注：JS 被禁用时不会有这个问题（.js 类加不上，图片本来就可见）， 所以这只影响「JS 正常 + 图片挂了」这一种组合。

修法：给同一个循环补一个 error 分支，把 is-loaded 也加上 （或者加一个 is-error 类，让灰底框改用 outline 描一圈红并显示 alt）。 顺带 lightbox.js 的大图也建议补一个 error 兜底 —— 那边影响小（黑底 + 说明文字还在），但同样是「点了没反应」。

2. skip link 会把自己顶到顶栏下面 —— #main 没吃到 scroll-margin-top P1

assets/css/critical.css:235-236 · layouts/_default/baseof.html:102

锚点落点的规则是这么写的：

main [id] { scroll-margin-top: var(--anchor-offset) }

这是个后代选择器。而 skip link 的目标 <main id="main"> 本身就是 main，不是 main 的后代 —— 所以它一条都没匹配到。

顶栏是 position: fixed（靠 body { padding-top: var(--header-h) } 让位）， 高度 64px。跳转时 #main 被滚到视口顶端（y=0），于是顶栏盖住了 main 的前 64px； 而 main.container 的 padding-top 只有 40px —— 页面标题的上沿被盖掉约 24px。

加上 scroll-margin-top: 76px 后，浏览器「希望」把 #main 放到 y=76 —— 但它已经在 y=64，只能上移不能下移 → 页面不滚动，标题完整可见。

修法：把那条规则的选择器从 main [id] 改成 main[id], main [id]（或直接写成 #main, main [id]）。 注意别在 html 上加 scroll-padding-top —— MAINTENANCE.md 里已经写明两个值会叠加、把标题顶到离顶部近 180px， 看着就像没对准。

二、交互一致性（做了，但只做了一半）

3. [ / ] 上/下一篇快捷键，在多数文章上是哑的 P2

assets/js/ui.js:83-96 · layouts/_default/single.html:135-150

ui.js 里的快捷键找的是 .post-nav-prev / .post-nav-next：

var link = e.key === "[" ? document.querySelector(".post-nav-prev") : document.querySelector(".post-nav-next");

但 single.html 里 .post-nav 和 .related-posts 是 互斥的 —— 相关文章有内容时渲染前者，{{ if not $relatedPosts }} 才渲染后者。 而 [related] threshold = 60、标签权重 100，只要共用任意一个标签就算相关， 所以多数文章都有相关文章 → 这两个元素根本不存在 → 按键静默无反应。

而且全站没有任何地方提示过这两个键（搜索面板的 footer 只写了 ↑↓ / Enter / Esc）。 功能既不可发现、又有一半失效。

三选一：① 相关文章下面总是再渲染一遍 .post-nav （顺带解决「有相关文章时就没有上/下篇导航」这个更明显的问题，我倾向这个）； ② 让快捷键退化为「跳到相关文章的第一条 / 最后一条」； ③ 干脆删掉这个快捷键，减掉一处没人知道的机关。

4. 搜索面板的 listbox 只做了一半：看得见，听不见 P2

assets/js/search.js:35-45、350-358

面板里有完整的 ARIA 骨架：容器 role="dialog"、 结果区 role="listbox"、每条 role="option"。视觉上也确实有反馈 —— .search-result.is-active { background: var(--surface-2) }。

但 setActive() 只切了 .is-active 这个类， 从头到尾没设过 aria-selected；输入框也没有 role="combobox" / aria-controls / aria-activedescendant。 所以读屏用户听不出当前选中了哪一条，只知道「有个列表框」。

另外 role="option" 会把 <a> 的 link 语义顶掉， 读屏不再念「链接」—— 这一点配合上面缺失的选中态，整个列表框对外是「半透明」的。

修法：setActive() 里同步 el.setAttribute("aria-selected", ...)； 给输入框补 role="combobox" aria-expanded aria-controls aria-activedescendant， 并给每条结果一个稳定 id（可以用文章 URL 或序号）。

5. 灯箱打开时没有任何加载态 P2

assets/js/lightbox.js:84-92

render() 直接把 src 换成 1600w 的变换图， 没有任何 loading 指示、也没有 error 兜底。 慢网络或大图时，点开是一整屏纯黑，只有右上角关闭按钮和底部计数 —— 读者的第一反应是「坏了」，而不是「在加载」。

正文里的缩略图是 960w，灯箱要的是 1600w，所以这不是同一张图、必然要重新下载 （这也是 Image Transformations 的代价，本身是合理设计）。

修法：给 .lightbox-img 挂 load / error： 加载中在计数那一行显示「加载中…」（或给图加一层轻微脉冲）， 失败时把说明文字换成「图片加载失败」。成本很低，但对慢网的观感差别很大。

三、加载：还能更精确的地方

这两条都不是缺陷，是「预连接打得比实际需要早 / 不够准」，收益很小。 列出来是因为你问了，而不是因为它们值得优先做。

优先级问题说明与修法
P3 图床的 preconnect 在每一篇文章页都发，但约一半文章正文里没有图 baseof.html:30 的 $hasImageCDN 是 or (in .Content $imageHost) (and site.Params.donate.enabled ...) —— 后半句让所有 posts / weekly 都成立。而打赏码在 donate.html:12 是 <details> 里的 loading="lazy" 图，不展开根本不请求。 所以对「正文无图」的文章，这次 TCP+TLS 是纯白开。 修法：去掉 and site.Params.donate.enabled … 那半句， 只按「正文里真的有图床图」判断。
P3 giscus 的 preconnect 没带 crossorigin baseof.html:21 是 <link rel="preconnect" href="https://giscus.app">， 而 giscus.js:113 给 client.js 设了 script.crossOrigin = "anonymous" → 那个脚本是 CORS 模式取的，不会复用这条「无 crossorigin」的预连接。 好消息是 giscus 的 iframe 导航会复用它，而 iframe 才是大头 —— 所以现状不算错。 想两段都吃到，再补一条 crossorigin 的 preconnect。
另外这条预连接在页面加载时就发起，而 giscus 要到滚到评论区前 400px 才注入 —— 不往下滚的人会白付一次连接。这个提前量可以接受，只是让你知道。

四、复查确认没问题的（不用管）

  • 正文图宽高 100% 齐全 → 正文零 CLS。data/image_dims.json 有 310 条，content/ 里正好 310 处图床图片 —— 数字完全对上。
  • .lightbox[hidden] / .search-panel[hidden] 都显式写了 display: none。这一点值得夸：两个弹层都是 position: fixed 的类选择器， 如果不显式写这条，UA 的 [hidden] 会被类选择器压掉、弹层永远看得见 —— 这是非常常见的坑，这里避开了。
  • 2026-09-30 那轮交互修复都还在。[data-close] 复数绑定（灯箱 X + 搜索 Esc 按钮）、 灯箱滑动换图、焦点陷阱（focus-trap.js 用 capture 监听 + release() 解绑）、 移动端菜单点空白处关闭 —— 逐条复查，代码都在。
  • prefers-reduced-motion 是全站生效的。重置写在 critical.css 的 *, *::before, *::after 上，而 critical.css 每页内联 → 异步包里的 .lightbox-backdrop { animation: overlay-in } 也照样被压掉。
  • Speculation Rules 用的是 moderate，手机上不会白预渲染。 桌面上是 hover 触发；触屏是 pointerdown，等同于 conservative。 所以「滑过链接就整页预渲染」这件事在手机上不成立。
  • 统计和评论都对 document.prerendering 做了判断。 GoatCounter 走 requestIdleCallback、giscus 等 prerenderingchange —— 预渲染不会污染统计，也不会白拉评论。
  • giscus.js 是单独打包 + defer + SRI，只在带评论的文章页加载， 没有塞进全站 bundle。
一个已知的老问题，这次没条件复核：首页 / 的边缘缓存 （MAINTENANCE.md 第 4b 节记的 cf-cache-status: HIT）。 它最严重的后果不是「内容旧」，而是改 CSS 会换指纹文件名、边缘那份旧 HTML 指向已删的旧文件 → 404 → 整页没样式。这条只能靠 curl 实测， 这一轮 Bash 不可用所以没查 —— 你下次在终端跑一遍那三条 curl 就能确认。
