二、诊断：三个可数的机制

「还缺什么」不该停在形容词上。下面是三处能数出来的具体缺口 —— 前两个是「功能其实写好了，只是没被渲染」，第三个是「信息已经在别处算过，首页没接」。

① 文末「上一篇 / 下一篇」在每一篇文章上都不出现 —— 它被「相关文章」挤掉了

看模板 layouts/_default/single.html:123-150：

  • {{ if $relatedPosts }} → 渲染「相关文章」
  • {{ if not $relatedPosts }} → 渲染「上一篇 / 下一篇」

这是二选一。而复算构建产物的结果是：

复算（产物，不是源码）

grep -rl 'class=related-posts' public/posts | wc -l → 124（= 全部文章页）
grep -rl 'class=post-nav' public/posts | wc -l → 0
grep -rl 'post-nav-card' public/ | wc -l → 1，且那一个命中的是 public/css/site-core-post.min.….css，没有任何 HTML 里出现过。

124 这个数和内容侧对得上：content/ 共 133 个 .md，减去 9 个 _index.md / 单页（about / privacy / archive / friends / media / tags / categories / posts 栏目页）正好 124 篇 posts + weekly。

也就是说：文章页永远只给「相关文章」，永远不给「翻下一篇」。首页和归档页能按时间顺序一路读下去，到了文章页反而断了 —— 对 24 期周刊这种天然连载尤其别扭。

还有一处连带失效：assets/js/ui.js:89-95 里 [ / ] 两个快捷键的实现是去 click() .post-nav-prev / .post-nav-next。那两个元素既然不渲染，快捷键就是静默失效的 —— 不报错、不提示，按了没反应。

关键在于：这不是「没做」，是「做了一半」。功能、样式（post.css:10-42 里 40 多行 .post-nav / .post-nav-card）、快捷键、打印隐藏规则全都写好了，只差模板里那一个 if。

② 系列文章没有出口 —— 内容已经在，读者找不到下一 part

站点里有两组天然连载，共 10 篇：

  • 《综述写作之-》5 篇：确定主题 / 文献管理 / 投喂文献（上）/ 投喂文献（下）/ 作图工程
  • 《居家流水账-》5 篇：第一天 ~ 第五天

这 10 篇之间现在唯一的关联是「相关文章」（最多 3 篇，按 tags / categories / date 打分，顺序由分数决定）和分类 / 标签页。实测：review-feeding-1（投喂文献上）文末的相关文章里有没有「投喂文献下」全看打分 —— 读者读完上篇，不保证能顺畅走到下篇。周刊的「上一期 / 下一期」更是从设计上就不存在。

content/ 的 front matter 目前只有 title / slug / summary / description / categories / tags / comments / draft 这几个字段，没有任何字段能表达「这五篇是一组」。

③ 首页第一眼看不到「这个站有多大」

归档页有一行统计（_default/archive.html:12）：

共 <strong>124</strong> 篇文章 · 今年写了 <strong>N</strong> 字

首页只有一句「总得留下点什么吧」+ 时间线（layouts/index.html:7-9）。第一次来的读者在首页拿不到坐标 —— 这是个什么站、写了多久、有多少东西。而这段数据模板里已经算过了（archive.html:8-9 的 $yearChars），搬到首页是几行的事。

B · 设计 / 观感

B1P1

文末四级节奏要重新定一次

现在的顺序是「正文 → .post-end 完字章 → 相关文章 → 评论」，间距是 --space-10 / --space-8 / --space-12。加上系列条与一行式上下篇之后，文末变成「落款 → 系列 → 相关 → 上下篇 → 评论」五段，需要一次明确的节奏定义（哪几段之间用发丝线、哪几段只靠间距）。

改：assets/css/post.css · critical-post.css 的 .post-end

为什么：这是 A1 / A2 的配套动作。DESIGN.md 的「线的语法」只允许两种线，五段结构如果不指定哪几段有线，很容易又长出四套线语言 —— 那正是归档页 2026-10-02 才收敛掉的问题。

B2P2

把「签名时刻」定稿

DESIGN.md 的 Known Gaps 里挂着一条：「印章『签名时刻』的具体形态（尺寸 / 位置 / 是否做旧）尚未定稿」。目前全站唯一的红章是文末 .post-end 那个 46px 的「完」。

改：layouts/index.html 或 layouts/_default/about.html · assets/css/critical*.css

为什么：这是设计系统里唯一一条悬而未决的决策。首页卷首或关于页头像旁是天然的候选位。注意 DESIGN.md 明写「只此一处，不要复制到每个标题」。

B3P2

全站仅剩的两处未复核红

.post-cat-chip::before 的 ●（critical-post.css:39-43）和 .post-tag-chip::before 的 #（critical-post.css:988-992）现在是 --accent 印章红。这是 DESIGN.md Roadmap P2 里明确登记的待办（连同阅读进度条）。

为什么：它们是纯装饰前缀符号，不承担「可交互 / 当前状态」语义。要么降为 --muted（和标签文字同色，读成一体），要么承认它们是「可点的目标」而保留 —— 但要选一个并写进文档，别让它一直挂在待办里。

D · 现代化

D1P1

Service Worker：让「添加到主屏幕」真的能用

site.webmanifest + 图标 + apple-mobile-web-app-* 全都配好了，但没有 Service Worker —— 所以从主屏图标打开时是联网加载的，断网就是浏览器错误页。

新增：static/sw.js + baseof.html 里注册 · static/_headers 里给 /sw.js 加 Cache-Control: no-cache

为什么：一个纯静态博客做 PWA，SW 是唯一缺的那块。缓存策略建议「HTML 走 network-first、/css/* /js/* 走 cache-first」—— 因为 CSS / JS 已经带指纹（fingerprint），可以永久缓存。

D2P2

面包屑的结构化数据

视觉上面包屑已经有了（single.html:19-29 的「首页 › 分类 › 标题」），但 head-meta.html 的 JSON-LD 只有 BlogPosting / Person / WebSite，缺 BreadcrumbList。

改：layouts/partials/head-meta.html

为什么：搜索结果里能显示路径层级，纯 SEO 小收益，十几行模板。

D3P2

RSS 补 <atom:updated>

RSS 现在只输出 pubDate，没有「更新于」的时间戳 —— 而站内文章页是有「更新于」的（靠 sync-lastmod.py 刷）。

改：layouts/_default/rss.xml

为什么：订阅端能感知到文章被修订过。数据现成（.Lastmod）。

五、不该加（以及为什么）

这一节和「值得加」同样重要 —— 有些功能对别的博客是好主意，对这个站是负债。

看起来该加结论理由
Mermaid 图表不做content/ 里出现 0 处，加了就是死代码。bearneo 也只在 .Params.mermaid 为真时才加载 —— 我们连这个参数都没有。
KaTeX / MathJax 数学公式不做（暂时）实测全站正文里 $…$ / $$…$$ 出现 0 次。等真写了带公式的科研文再加，而且必须按「这一页用到才加载」的做法，绝不进全站包（否则每页多背几十 KB）。
Upvote / Kudos 点赞不做这是 bearneo 唯一真正需要后端的功能（Cloudflare Workers + D1）。工程量过夜、收益不确定，而且会和 giscus 的反应功能重复。
卡片化 / 毛玻璃 / 大圆角不做与「纸账 + 印章」直接冲突。DESIGN.md 的 Don'ts 已明写：不要给列表卡片套白底 + 投影 + 大圆角；不要用毛玻璃做常驻页头。
第二个强调色不做全站只有印章红。DESIGN.md：「稀缺才有力量。」

七、需要你拍板的一个问题

A1 会让文末变长。现在文末是「相关文章 3 行」就结束；并存之后是「相关文章 3 行 + 上下篇」。你要哪一种？

(a) 两者都留 —— 上下篇继续用现有的两张卡片。

信息最全，但文末最长：.post-nav-card 是 padding 20px + 两张并排，加上 .post-nav 的 margin-top: 56px，比现在多出约 180px。

(b) 只留上下篇，砍掉相关文章 —— 回到「按顺序连载优先」。

文末最短，但会丢掉「同一话题的横向发现」。而且相关文章是现在唯一的横向出口，砍掉之后 tags / categories 就成了唯一的发现路径。

(c) 相关文章保留，上下篇压成一行文字（Mockup A 右栏就是这个方案）。

我倾向这一个。它同时解决两件事：① 文末只多约 30px；② 上下篇本来就是「按顺序走」的线性导航，一行文字比两张卡片更贴合「账本」的比喻，也和 .post-row 那一套「标题 + 发丝线」的语言一致 —— 卡片是「两条并列的选项」，而上一篇 / 下一篇从来不是并列的。
