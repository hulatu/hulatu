一句话结论

那篇文章列的 8 个技法里，5 个对本站不适用（而且原因都是可验证的，不是「感觉不适合」）； 真正值得搬的只有 2 条，但都是一次性改动、零回归的。

本站与 Apple 的差距不在视觉语言 —— 纸 + 发丝线的克制，Apple 反而没有； 差距在中文排版的两处手艺：中英混排的自动空距，和标题的孤行保护。 这两件事，正是那篇文章花最多篇幅讲的。

值得搬 ①　中英混排的自动空距

文章的第五节讲「盘古之白」。本站的做法是人工在源码里加空格，这与 Apple 一致（文章说 Apple 内部把加空格写进了文案规范）。 但人工做法有一个可量化的代价：

已加空格（正确）
1540处 · CJK + 空格 + 拉丁/数字
漏加（紧贴）
213处 · 如「定好20分钟」「在观看B站视频」
涉及正文文件
133个 .md（已剔除代码块与行内代码）

也就是说，同一篇文章里会同时出现「加了空格的」和「没加的」。这不是审美问题，是人工流程必然的漏。 2025 年 11 月起，CSS 给了原生解法，而且一行就够。

为什么它能一行搞定，以及三个必须知道的坑

必须显式声明
默认关闭规范初始值是 normal，但所有浏览器实现都改成了 no-autospace（性能考量）—— 不写就永远不生效
不会双倍空格
insert 语义默认等价于 insert：只在没有空格处补，已手打的 1540 处不动
与字距相加
additiveMDN 明写：letter-spacing 的量会叠加在自动空距之上

坑 1 —— 补出来的空距比你手打的窄。我量了本站两个主字体的 U+0020：

字体用在哪U+0020 宽度17px 下与自动空距比
Songti SC标题（衬线）0.250 em4.25 px标题里完全一致，无观感差
PingFang SC正文（无衬线）0.333 em5.66 px正文里自动空距更窄

浏览器插入的确切宽度由实现决定（规范与各家资料的口径在 1/8–1/4 em 之间不一致，落地后以实测为准）。 结论是：标题里可以放心开（Songti 的 0.25em 与手打空格同宽）；正文里会出现「新补的比原有的窄一点」， 一段话里两种空距相邻时理论上看得出来，实际上 17px 下差约 1.4px。

坑 2 —— replace 目前 0 支持。「把已有空格统一替换成规范空距」听起来正好治上面这个不一致，但 insert 只有 Firefox 支持、replace 截至 2025 年底没有任何浏览器支持。所以不要写它，写了两件事都白搭。

坑 3 —— 代码块必须排除。等宽对齐会被自动空距破坏：

/* assets/css/critical.css 的 :root 里，紧挨着字体栈那段 */
:root {
  text-autospace: normal;   /* = ideograph-alpha + ideograph-numeric */
}
/* 等宽内容一律关掉，否则代码块的中文注释会错位 */
pre, code, kbd, samp { text-autospace: no-autospace; }

放 critical.css 而不是异步包：正文首屏就要用到，晚一拍会看到整页文字「抖一下」。 这条改动只增不减，回滚就是删两行。

值得搬 ②　标题的孤行保护

这是文章里最「Apple」的一条：把段落末尾那个词包进 <span class="nowrap">， 让它不被单独甩到下一行。文章举的例子是「碳排放。」被保护后，末行不会只剩「放。」。

为什么是「末 2 字」，而不是 3 字或 4 字

关键在于保护末 N 字只对「末行恰好 1 字」的标题生效。若一条标题的末行本来就有 2 个字（如「世界」）， 保护末 2 字并不会改变断点 —— 断点本来就在它们前面。所以：

  • 保末 2 字：只动那 8 条孤字标题，其余 119 条零变化。
  • 保末 3 字：会连「末行 2 字」的标题一起动（手机端另有 7 条），首行还要再短一个字。
  • 保末 4 字：Apple 中文站就是这个量级，但实测首行会被拉掉 3–4 个字（手机上 12 字 → 9 字），换行节奏明显变了。

代价要说清楚：首行会比现在短 1 个字（手机上约 28px / 350px = 8%）。

怎么实现

Hugo 侧新建一个 partial，把标题的末 2 个字包起来，在渲染标题的地方调用：

<!-- layouts/partials/orphan-safe.html（新建） -->
{{- $t := . -}}
{{- $n := countrunes $t -}}   <!-- 必须用 countrunes：len 对字符串返回的是「字节数」 -->
{{- if gt $n 2 -}}
  {{- $head := substr $t 0 (sub $n 2) -}}
  {{- $tail := substr $t (sub $n 2) -}}
  {{- printf "%s<span class=\"nowrap\">%s</span>" (htmlEscape $head) (htmlEscape $tail) | safeHTML -}}
{{- else -}}
  {{- $t -}}
{{- end -}}

调用点：layouts/_default/single.html 的 <h1 class="post-title">， 以及四个列表行 partial（post-row.html / post-row-compact.html / post-row-minimal.html / archive.html）—— 手机端列表行也有 2 条孤字。

两个必须注意的实现细节：① len 在 Hugo 里对字符串返回字节数，中文会算成 3 倍，一定要用 countrunes； ② 拼 HTML 前要 htmlEscape，否则标题里的 & 会破坏标记。

搬不了的两条，以及证据

Apple 那两个「变态细节」—— 汉字调小、全角标点收窄 —— 都建立在同一件事上：Apple 自己发了一款字体 （SF Pro SC，非公开、只用于简体中文官网）。本站的设计系统明确「不下载外部字体」，所以这条路直接封死。

但文章没讲的是：CSS 层其实有个原生替代 text-spacing-trim（收紧 CJK 标点）， Chrome / Edge 123+ 已默认开启。听起来正好能补上这个缺口 —— 可惜对本站无效。我查了两个主字体的 OpenType 表：

字体用在哪GSUB 表haltchwspalt
Songti SC Regular标题没有 GSUB 表———
Songti SC Bold标题没有 GSUB 表———
PingFang SC Regular正文25 个特性无无无

MDN 在 text-spacing-trim 里写得很明确：「字体必须带 halt 或 chws 特性； 两者都没有时，text-spacing-trim 会被禁用。」 本站两个主字体恰好都没有 —— 所以写上去是个静默无效的声明，比不写更糟（下次有人会以为它在起作用）。

顺带：Safari 的常见兜底写法 font-feature-settings: "halt" 1 同样无效 —— Songti SC 连 GSUB 表都没有， 请求一个不存在的特性就是空转。这条也一并否掉。

剩下三条「不适用」，理由都很短：

  • 响应式换行 <br class="small"> —— Apple 用在「想升级，时机正正好。」这类固定标语上。本站唯一的固定标语是首页卷首「总得留下点什么吧」（9 字），三档断点下都不换行，没有需要控制的地方。
  • 居中标题的视觉校正 —— 这条要成立，得先有「居中 + 末尾带标点」的标题。全站居中大标题只有首页卷首一个（.site-hero 是 text-align: center），内容是「总得留下点什么吧」，不带标点；.page-title 与 .post-title 都是左对齐。（关于页的 .about-name 也居中，但那是姓名不是标题，同样不带标点。）
  • 文案本地化 —— Apple 改写「9 月 18 日」是为了规避风险，个人博客没有这个场景。

你已经赢过 Apple 的地方

这部分不是客套。诚实地列出来，是为了避免下次再花时间「向 Apple 靠拢」那些你已经做得更好的事：

  • 零字体请求。Apple 简体中文官网首屏要下载 SF Pro SC（非公开、还得和 SF Pro Display 混排）。本站用系统栈，一个字体请求都没有 —— 这既是性能，也是 Bear Blog 血统带来的审美。代价就是上面那两条搬不了。
  • <html lang="zh-CN"> 早就写好了。这是 text-autospace 能生效的前提，也是浏览器走对 locl 与断行规则的前提 —— baseof.html:3。
  • 关键 CSS 内联，首屏 0 个阻塞请求。首屏用得到的规则全在 critical.css 里内联进 <head>，异步包只装滚动后才出现的东西。这套「首帧用不用得到」的归属判据，Apple 官网没走这条路。
  • 排版纪律是成文的。DESIGN.md 480 行、MAINTENANCE.md 记着每条「故意这么设计」的理由。Apple 不会公开这个 —— 本站的每条规则都能被引用、被复算、被推翻。
  • 现代 CSS 已经吃得很透。view-transition-name（跨页面标题过渡）、:has()（图片加载失败的虚线框）、color-mix()（水印色）、clamp() 都在用。这次要加的 text-autospace 是同一批东西。

要保留的（别在「现代化」的名义下改掉）

  • 不下载外部字体。这是本站能「零字体请求」的唯一原因，也是上面两条搬不了的根源。它是取舍，不是缺陷 —— 别为了对齐 Apple 去加载思源宋体。
  • 标题 text-wrap: wrap，不要 balance。你 2026-10-02 已经用真实数据否掉过它。孤行保护是定点修（只动 8 条），balance 是全局改（每条多行标题都变短）—— 两者不能混为一谈。
  • 纸 + 发丝线的层级。Apple 官网是满屏产品图 + 大圆角卡片 + 毛玻璃导航，那是「产品发布页」的语言。本站是账本，两者不该互相靠拢。
  • 单一印章红。Apple 用彩色产品图承担视觉，本站用一枚红章。这次的清单里没有任何一条要动红。
  • 人工加空格的既有内容不用回改。text-autospace 是 insert 语义，只补不覆盖 —— 1540 处一个都不用动。

需要你拍板的一个问题

孤行保护会让首行比现在短一个字 —— 这与「标题排到最右再换行」有轻微张力

你 2026-10-02 定下的规矩是：标题让它排到最右再自然换行，孤字是自然换行的偶发代价，不是缺陷。 这条规矩我认同，而且它挡住了 balance。

但 Apple 的做法是第三种可能 —— 既不用 balance，也不是放任： 只把末尾那 2 个字包起来。它只影响「末行恰好 1 字」的 8 条标题，其余 119 条一动不动； 代价是这 8 条的首行会短 1 个字（手机上约 28px）。这算不算破坏了你原来那条规矩？

  • 方案 A（推荐）
    保末 2 字。只修 8 条孤字标题，119 条零变化。首行短 1 字，但末行不再是孤零零的一个字。
  • 方案 B
    保末 3 字。更彻底（末行至少 3 字），但会连「末行 2 字」的标题一起动，首行短 2 字，影响面扩大到约 17 条。
  • 方案 C
    不动 CSS，沿用你原来的判断 —— 觉得哪条标题孤得难看，就改那条标题的文案。零风险，但要人记着。

本页是评审，没有改任何代码。所有数字来自仓库现算： 标题断行用真实 Songti.ttc 的 hmtx 度量 + 贪心断行脚本； 中英空距统计扫描了 content/ 下 133 个 .md（已剔除 front matter、代码块与行内代码）； 字体特性用 fontTools 读 GSUB 表。

确认方案后我再动手 —— 按你的习惯，可以只挑一个子集。
